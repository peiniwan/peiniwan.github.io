7-图片低配系统 oom 优化

背景

通过对 Android 1.14.0-2.2.3 版本 bugly 的监控来看，我们发现大量的 oom 问题，而且大部分发生在 Android 8.0 以下，学习机居多，随着业务复杂性，大量图片的引入，这些设备 heapsize 普遍较小，这个问题越来越严重，需要迫切解决在 Android 8.0 以下图片的加载稳定性，在前期的 2.0-2.3 我们做了以下工作，尽量解决一部分问题

1、增加 heapsize

设置了 largeHeap,通过系统 api 申请更大的 heapsize,效果甚微
在 Android 中，每个应用进程（Java/Kotlin 层）的内存有一个虚拟机堆（Dalvik/ART Heap）限制，用于存放 Java 对象。如果超出堆限制，就可能出现 OutOfMemoryError（OOM）。这个堆限制不是固定值，而是根据设备内存、ROM 配置和是否请求大堆等因素而定


2、排查本地的大图

对本地引入的大图通过压缩，大幅度减少图片的 oom，这个在新人礼弹窗和新手引导效果比较明显

3、图片远端裁剪

通过阿里云 oos 提供的通道命令，通过拼接尺寸和图片格式。获取指定大小和格式的图片。而不是全部使用原图加载

4、扫描引擎

图书端扫描功能使用频率较高，在扫描过程中，大量 bitmap 创建和回收，造成内存抖动比较严重，oom 问题频发，我们采用在 Android 7.0 及 以上采用最新版本的 zxing 引擎，在 android 7.0 以下使用华为的扫描服务。这个服务是基于 Ai 离线模式，特别在华为设备上，直接调用华为系统的扫码能力，大大减少图片的处理操作，扫描引擎上线后，扫描 oom 问题彻底解决

上图是从 bugly 平台抓取的一个 oom 堆栈，大部分都是 bitmap 创建不足，oom 的时候 java heap 中占用最多的对象是 bitmap,通过调研一些文档，我们得到以下结论

1、OOM 的分布主要在 Android 8.0 之前 heap size 较小的设备
2、OOM 是 Java heap 中占用内存较多的是 Bitmap（确切的说是 Bitmap 的像素数据），当 Bitmap 像素占用内存在 Native Heap 分配时，即便 heap size 很小，应用也不容易 OOM

目标就变成在 Android 8.0 之前 bitmap 的内存也从 Native 层分配

方案

通过参考抖音 android 性能优化的方案，实现了 hook 对应 android native 层的代码，同时为了 hook native 层使用了字节的一个开源库-ShadowHook【一个 Android inline hook 库，它支持 thumb、arm32 和 arm6】
想要使得 Android 8.0 之前的设备 Bitmap 像素内存也分配在 Native heap，需要先把 Bitmap 的创建流程调查清楚。

  1. allocateJavaPixelRef，是 8.0 之前版本为 Bitmap 像素从 Java heap 申请内存
  2. allocateHeapBitmap，是 8.0 版本为 Bitmap 像素从 Native heap 申请内存
    原理是：改成从 Native heap 申请内存，创建bitmap

private static ArrayList<Bitmap> sBitmapCache = new ArrayList<>();

void testNativeBitmap(Context context) {
    // 开启某种原生位图优化（可能是一个第三方库或自定义方法）
    NativeBitmap.enable(context);

    for (int i = 0; i <= 5000; i++) {
        // 从资源文件中解码图片
        Bitmap bt = BitmapFactory.decodeResource(context.getResources(), R.drawable.icon);
        
        // 每加载 100 张打印一次日志
        if (i % 100 == 0) {
            Log.e("hanli", "loadbitmaps: " + i);
        }
        
        // 将 Bitmap 添加到静态缓存列表中
        sBitmapCache.add(bt);
    }
}
