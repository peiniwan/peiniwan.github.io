WebSocket

聊聊 OkHttp 实现 WebSocket 的细节：鉴权、长连接保活与实现原理

一、为什么需要 WebSocket

在传统的客户端—服务端通信模型中，最常见的是 HTTP 轮询：

  • 客户端定时发起请求

  • 服务端返回当前状态

  • 即使没有新数据，也会产生一次完整的 HTTP 请求

轮询的缺点非常明显：

  • 大量无效请求浪费网络和服务器资源

  • 实时性差，延迟依赖轮询间隔

  • 移动端功耗高，不利于长时间在线

在需要实时消息、推送、状态同步的场景下（如 IM、直播信令、协作工具），HTTP 轮询并不合适。

二、WebSocket 是什么

WebSocket 是一种 建立在 TCP 之上的应用层协议，用于实现真正的全双工通信。

2.1 WebSocket 的核心特性

  • 基于 TCP，连接建立后保持长连接

  • 全双工通信：客户端和服务端都可以主动发送消息

  • 握手阶段复用 HTTP，不易被防火墙和代理拦截

  • 数据传输不再携带冗余 HTTP Header，通信更高效

2.2 WebSocket 与 HTTP 的关系

WebSocket 并没有重新设计 URL 体系，而是沿用了 HTTP 的 URL 格式，只是协议标识符发生了变化：

  • ws:// —— 明文 WebSocket

  • wss:// —— 基于 TLS 的安全 WebSocket

三、WebSocket 的数据帧模型

WebSocket 建立连接后，所有数据都通过 二进制帧（Frame） 进行传输，常见的包括：

3.1 数据帧（MESSAGE）

  • 用于真正的业务数据传输

  • 支持文本（String）和二进制（ByteString）

  • 大数据会被拆分成多个帧发送

3.2 控制帧（Control Frame）

  • PING：主动保活心跳

  • PONG：对 PING 的响应

  • CLOSE：主动关闭连接

五、WebSocket 鉴权的常见方式

WebSocket 的鉴权通常发生在握手阶段，也就是 HTTP Upgrade 请求时。

5.1 常见鉴权方案

  1. URL 参数鉴权

  2. HTTP Header 鉴权（推荐）

  3. 连接建立后发送鉴权消息

    • 连接成功后发送一条 auth message

    • 服务端验证通过后才允许后续通信

工程上更推荐 Header 或首包鉴权，避免 token 暴露在 URL 中。

六、WebSocket 长连接保活机制

6.1 为什么需要保活

WebSocket 是长连接，但：

  • 服务端通常会对长时间无数据的连接进行清理

  • NAT / 防火墙也可能回收空闲 TCP 连接

因此，客户端需要定期发送心跳来证明连接仍然活跃。

6.2 OkHttp 的 PING 保活机制

配置后：

  • OkHttp 会定时发送 PING 帧

  • 服务端收到后返回 PONG

  • 若长时间未收到响应，OkHttp 会认为连接异常并触发 onFailure

6.3 心跳间隔如何设置

  • 一般建议 小于 60 秒

  • 具体值需与服务端协商

  • 过短会增加网络消耗，过长可能被服务端断开

非常适合单元测试和本地调试。

八、总结

WebSocket 作为一种基于 TCP 的全双工通信协议，非常适合实时通信场景。
而 OkHttp 对 WebSocket 的封装，使得客户端实现成本大幅降低。

本文核心要点回顾：

  • WebSocket 通过 HTTP 握手建立长连接

  • 使用 MESSAGE / PING / PONG / CLOSE 帧通信

  • OkHttp newWebSocket() 即可快速接入

  • 鉴权应尽量在握手阶段完成

  • pingInterval() 是实现长连接保活的关键

  • MockWebServer 可用于本地模拟和测试

在移动端工程中，合理使用 WebSocket + 心跳保活机制，是构建实时系统的重要基础能力之一。
